### 根因（已定位，未修）

commit `df4b458`（Z1169「走查模板评论止血」）在 `server/routes/comments.js` 的 `POST /comments` 加写入守卫：

```js
if (req.user.is_test || isWalkProbeContent(content)) {
  return res.status(403).json({ error: "该内容不符合社区规范，请修改后再发布" });
}
```

而 e2e 探针注册账号用 `@test.dev` 邮箱（`server/routes/auth.js` → `isTestEmail` → `is_test=1`），
于是**所有 e2e 账号的评论提交一律 403**：探针只填内容不校验错误码，前端又把 403 吞掉（无 toast、
清空输入框），表现为「发布评论未回写 20->20」。

双重影响：
1. 自动化验收彻底失去「评论」这一段覆盖（且因为降级成 pending，退出码仍是 0，闸门不会报警）。
2. 真实用户在服务端被守卫误拒时，前端同样静默吞错，用户看不到任何原因——体验上是「点了没反应」。

### 建议修法（交开发 loop，不在本轮动手）

- 守卫区分「夹具/探针」与「正常内容」：`is_test` 账号**不拦**，改为入库时打 `is_test` 标记，
  由清理脚本按标记回收（与 Z983 既有约定一致）；至少要让 e2e 探针走白名单路径。
- 或者在 `lib.mjs` 统一把非 2xx 的响应 `expect` 失败打印出来，别让 403 变成静默 PASS 邻域。
- 前端必须把 403 的 `error` 文案 toast 出来，不能清空输入框了事。
- `probe-round15.mjs` 应进 MANIFEST（核心评论链路不该是 pending）。

## 结论

1 个 pending 失败已定性为**回归 + 闸门盲区**，已在 `docs/FEATURES.md` 建阻塞项并标注 `[BLOCKING]`。
